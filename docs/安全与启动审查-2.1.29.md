# 2.1.29 安全与启动审查

审查日期：2026-10-09。插件基线为远端 `main` 的 `a962179`（2.1.28，已含两次诊断补丁）。

## 本次实际修改

- 调整显示页数只更新 `chat_truncation`，下次打开聊天时应用；移除为了显示调整而调用的 `reloadCurrentChat()`。
- 正则局部接口缺失时停止并提示，移除完整聊天重读回退。异步加载接口、等待分帧后重新检查聊天 ID、生成状态和停用代次，避免旧任务刷新后来打开的聊天。
- `unconfirmed` 普通点击记录不再于 30 秒后覆盖已保存的异常，包括 Web App 重启后的记录。资源错误不再升级为业务异常；业务错误关联最新指针。
- 设置诊断在 APP_READY 汇总已完成的 Resource Timing，最多保留四条设置传输，不再在 fetch 响应头到达时把上一条传输当成本次请求。`durationMs` 明确仅到响应头，完整下载查看 `settingsResources`。
- 汇总浏览器仍保留的设置传输总数及插件激活前开始的数量。资源计时缓冲区可能淘汰早期请求，计数不保证完整。
- WebKit 明确不支持 Long Task 时报告 `unsupported`，避免“observed 但零条”被误解为没有主线程阻塞。
- 导出只增加可见酒馆版本、是否在聊天、内存消息数、DOM 消息数及生成状态，不读取聊天正文、角色名或文件名，不额外发请求。
- 本插件设置未变化时跳过启动保存；版本迁移和用户实际修改仍正常保存。

## P0：官方风险仍需上游修复

只读核对官方 [release 提交 06bde939](https://github.com/SillyTavern/SillyTavern/tree/06bde939fb1e9c4c8d8641d810f0a916b5bce127)，当前版本标为 1.19.0。用户两份诊断只包含插件版本，尚不能确认实际安装的酒馆版本、分支或是否有额外补丁。

- [#5941](https://github.com/SillyTavern/SillyTavern/issues/5941)：`src/endpoints/chats.js` 的 `/get` 异常仍返回 HTTP 200 + `{}`，`getChatData()` 也可能把不可读文件折叠为空数组。`public/script.js` 的 `getChat()` 遇到非数组/空响应会清空内存；**catch 中同样调用 `getChatResult()`**。后者在空聊天时补开场白并保存。因此仅把服务端错误改成 500 不足以消除风险。
- [#6032](https://github.com/SillyTavern/SillyTavern/issues/6032)：`saveChatDebounced()` 仍只核对角色 ID 和组 ID，没有核对同角色内的聊天文件名。旧响应写入全局聊天和元数据前也缺少完整的加载代次校验。完整性 UUID 是身份检查，不能视为全部并发或旧聊天的覆盖保护。
- 最后五条只影响 DOM 分页；`measureChatPayload()` 只读最近四十条。插件不裁剪 `chat`、不保存 JSONL，也不拦截聊天响应体。

最小上游修复方案（本次未修改或安装上游代码）：

1. 读取接口区分“确认新建/不存在”和“已存在但读取失败/损坏”，后者返回明确错误。现有聊天不可读时不能伪装为空聊天。
2. `getChat()` 读取失败、解析失败或无效响应立即终止，不调用会创建开场白和保存的 `getChatResult()`；同时在加载期间禁止保存。原有完整内存状态应保留，失败时显示重试状态。
3. 异步加载开始时捕获角色/组/聊天文件名和加载代次；每次等待后，在修改全局数组、元数据、渲染或保存前校验。延迟保存也捕获并校验完整身份，切换时取消待执行保存。群聊采用相同边界。
4. 最小回归：已存在且无 integrity 的千条聊天，注入断网、500、200+`{}`、损坏 JSON 后磁盘不变化；同角色 A/B 切换并交换响应完成顺序时，不跨文件应用或保存。

本插件移除不必要重读，降低触发机会；**并未修复酒馆原生加载/保存，不能宣称已完全防止聊天丢失**。

## P1：失效点击和空白仍需现场证据

两份用户诊断都以扩展菜单 `unconfirmed` 结尾：down/up/click 捕获与冒泡齐全，没有已确认的遮挡或 capture 残留；这不能证明业务处理成功，也不能确定失效原因。源码中此前全局提前释放 capture 的行为已移除，焦点保护已避免向其他输入框夺焦。本次未新增全局拦截或猜测性焦点/选区重置。

截图显示顶部菜单及输入区可见，中间没有消息。仅凭截图不能区分网络读取、原生加载状态、其他扩展和渲染异常。导出时 `chatState.messages > 0` 且 `renderedMessages === 0` 可定位为内存已有消息但无消息 DOM；两者为零仍需结合原生网络错误判断，不能自动当作新聊天。本次不会为此自动重载、清空或保存。

真机最小验证：iOS 主屏幕 App 复制/剪切/粘贴后点击发送和菜单；出现空白时先复制诊断，再核对版本、消息数量和聊天请求状态。Chromium/单元测试不代表真机修复完成。

## P2：已确认重复读取，尚未安全消除原生瓶颈

官方 `public/script.js:getSettings()` POST `/api/settings/get`，解析完整响应后在扩展初始化期间，`quick-reply/index.js:loadSets()` 再 POST 同端点，实际只使用 `quickReplyPresets`。第二次完整传输和解析可由源码确认；插件调用栈出现在外层是因为它包装了原生 fetch，并非插件主动读取大型设置。

两份现场：APP_READY 从 62.490 秒升至 123.785 秒；插件激活前从 24.014 秒升至 48.902 秒；后一份多个无关端点也同时变慢。两份旧诊断中约 57MB/6.6MB 的 Resource Timing 可能是前一次设置传输，不能和 3–3.5 秒响应头耗时直接相加或归属于快捷回复。没有解析耗时证据，不能把全部等待归因于 JSON.parse。

安全的最小上游优化：在主程序首次响应解析后、扩展初始化前，向快捷回复交付 `quickReplyPresets`；消费完即释放引用，保留迁移、更新和初始化回调，无需保留整份设置或克隆响应。另一方案是只返回快捷回复预设的专用接口，让 `loadSets()` 读取；都需在上游实现和验证。本次不通过调用栈匹配篡改响应、不缓存大型设置、不删除预设或自动关闭快捷回复。

初始化中的 `/api/quick-replies/save` 可能来自迁移、渲染回调或启动脚本；现有堆栈未说明具体调用者。本次不阻止该写入，避免丢失合法更新。iOS 主屏幕 + Basic Auth 的缓存兼容保护保留。
