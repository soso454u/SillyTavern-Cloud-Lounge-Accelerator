# 2.1.31 启动与聊天审查

2026-10-11，先 fetch 并确认插件远端 `main` 为 `baa2f77`（2.1.30）。上游只读对照此前诊断明确的 [1.18.0 / 51ad27fb8](https://github.com/SillyTavern/SillyTavern/tree/51ad27fb86d39a3daca3adaa970375c9670c12df)，未连接用户酒馆或接触聊天文件。

## 慢在哪个区间

本次用户提供：APP_READY 136.54 秒、SETTINGS_LOADED 125.85 秒、插件激活到 SETTINGS_LOADED 85.92 秒、settings/get 约 30.8 秒完成。由此插件激活约在 39.93 秒，主要等待位于设置请求完成之后；SETTINGS_LOADED 后仍有约 10.69 秒。此前诊断已证明快捷回复还会再次读取设置，不能把 30.8 秒当作全部设置读取结束，也不能把这段空档直接归为 JSON.parse。

[getSettings()](https://github.com/SillyTavern/SillyTavern/blob/51ad27fb86d39a3daca3adaa970375c9670c12df/public/script.js) 的顺序为：响应 JSON 和内部 settings JSON 解析 → 原生设置应用 → `await loadExtensionSettings()` → `await emit(EXTENSION_SETTINGS_LOADED)` → onboarding（首启时）及 sampler 验证 → `emit(SETTINGS_LOADED)`。

[loadExtensionSettings()](https://github.com/SillyTavern/SillyTavern/blob/51ad27fb86d39a3daca3adaa970375c9670c12df/public/scripts/extensions.js) 先等待首次加载事件、发现扩展、manifest 和必要的自动更新，再 `await activateExtensions()`。后者在循环中逐个等待语言包、JS/CSS 和激活 hook；模块的依赖、顶层 await 和初始化也属于 script load 的等待。单个 hook 的 5 秒上限不限制这些 script load，也不限制后面的扩展设置事件订阅者。加速器 `loading_order = -900`，激活时已经处于这个循环内；它的 `onActivate()` 不返回 `startEnabledModules()` 的 Promise，因此没有把自身后台启动任务作为一个 85 秒的 hook 等待。

**当前证据能定位到剩余扩展激活 / 扩展设置回调区间，不能指认某一个扩展或证明全部耗时来自 activateExtensions。** 本版不改变初始化顺序、缓存策略或合法初始化保存。

## 少量计时的含义

诊断临时观测原生 `eventSource.emit()` 的四个启动事件起止，不改变订阅者顺序、参数、原始返回值/Promise 或错误，不读取事件参数。APP_READY 分发完成或插件停用时恢复自己的包装；若后来被其他包装接管，不覆盖它。没有改写上游文件。

导出中的 `markers` 新增 `EXTENSION_SETTINGS_LOADED`、`SETTINGS_LOADED`、`APP_INITIALIZED`、`APP_READY` 各自的 `_DISPATCH_START` / `_DISPATCH_END`，未完成或失败时不会伪造 END。`durations` 增加：

| 字段 | 实际边界 |
| --- | --- |
| `pluginToExtensionSettingsMs` | 插件激活 → 扩展设置事件开始；主启动路径中表示剩余 loadExtensionSettings 等待，不包含该函数开始到插件激活之前的部分 |
| `extensionSettingsListenersMs` | 扩展设置事件的全部订阅者等待 |
| `extensionSettingsToSettingsMs` | 扩展设置事件结束 → SETTINGS_LOADED 开始，含中间原生步骤 |
| `settingsListenersMs` | SETTINGS_LOADED 订阅者等待 |
| `appInitializedListenersMs` | APP_INITIALIZED 订阅者等待 |
| `appReadyListenersMs` | APP_READY 订阅者等待，含原生欢迎页和其它订阅者 |

原有 APP_READY 标记仍表示本插件监听器执行时刻；新的 dispatch start 表示真正开始分发，end 表示全部订阅者完成。单个扩展初始化和 JSON 解析仍标注未观测。若初始化卡住，已发生的起止标记仍会随原有诊断限频保存，不必等 APP_READY 才保留证据。

## 已确认并移除的插件风险

- 2.1.30 桌面等非 iOS 设备在 SETTINGS_LOADED 中直接隐藏 `app-init`，但之后还要读取头像/角色/背景、初始化 tokenizers 和其它界面。本版移除此路径，所有设备由原生流程关闭遮罩。
- `recoverWelcomeScreen()` 在 APP_READY 或 online 时额外调用 `openWelcomeScreen({ force: true })`。原生函数确实会在 recent 请求后检查聊天 ID，但随后渲染模板、加载助手仍有异步等待；force 分支会清空全局 chat 和聊天 DOM。额外任务在角色切换中不能由调用前的单次检查安全约束。本版移除这套自动恢复及通知，不用延迟重试或另一次聊天读取替代；原生欢迎页继续自行处理。

**遮罩提前 8.44 秒并不能单独证明由插件提前撤罩导致。** 原生启动函数也会在 APP_INITIALIZED 后隐藏 loader，再分发 APP_READY；欢迎页通过 makeFirst 注册，原生 emit 顺序等待所有监听器，因此旧诊断的 APP_READY 监听器可能晚于实际分发开始。新计时能区分就绪前初始化与 APP_READY 内欢迎页/其它回调的等待。本版不擅自增加第二层遮罩或改写上游关闭时机。

## 聊天覆盖风险仍在上游

同一确切提交中，`getChat()` 对非数组/空响应清空内存，catch 仍调用 `getChatResult()`；后者在内存为空时补开场白并 `saveChatConditional()`。服务端读错误可能返回 200+`{}`，不可读文件也可能被折叠为空数组；已有聊天的完整性字段可能因此丢失。同角色内切换聊天时，延迟保存只校验角色/组而没有校验文件名；读取响应也缺少完整的加载代次保护。详见[之前的安全审查](安全与启动审查-2.1.29.md)。

本版只去掉插件的额外危险触发路径。聊天读取的 HTTP 错误和网络异常原样交给原生调用者；不克隆或解析聊天响应，不把错误转换成空数组，不自动重载、清空、补开场白或保存聊天，不拦截合法保存。**它没有修复上游失败后保存的语义，不能保证所有聊天覆盖风险已消除，也不能据此认定此前已恢复的覆盖事故就是加速器造成。**

只运行仓库自动测试。新增隔离回归覆盖启动事件/联网不触发额外恢复、失败读取和保存请求保持原样、晚注册异步订阅者计时、原始 Promise/错误/参数保留，以及完成或停用后的包装恢复。测试使用模拟消息和请求，没有打开实际角色卡、读写 JSONL、注入真实网络故障或修改 SillyTavern 上游。136.54 秒的现场是否改善、具体扩展是谁，仍需下一次启动的新增分阶段数据确认。
